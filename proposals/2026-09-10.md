# Group 2 Daily Proposals — 2026-09-10

## Top item: the bot has been stuck in a crash-restart loop most of today — no new trading has been possible

**What**: A code fix (two complementary changes, described below as diffs — not applied) to
`regime_router.py` and `scripts/watchdog.sh`.

**Why**: I read `watchdog.log` and `bot.log` before looking at any trade signal, because the
context file's 100 "recent signals" were all timestamped in a single 13-minute window
(05:33–05:46 ET) with nothing since — that gap turned out to be real, not a quiet market.

`watchdog.log` shows 17 restarts today, starting at 2026-09-10T00:01 UTC and continuing
through the current restart at 13:40 UTC (i.e. spanning last night through this morning ET),
almost all with the same reason: `status=trading but no iteration has ever completed,
trading started ~173-235s ago`. `bot.log`'s own telemetry confirms `orders_filled: 0` for
every single snapshot logged today — the one `positions_tracked: 1` is a pre-existing
position, not a new fill. The 100 signals in `context_2026-09-10.json` all come from the one
~60-minute stretch (roughly 04:49–05:50 ET) where the bot happened to stay up long enough to
actually iterate; every other 60s cycle since then has been killed by the watchdog before it
could finish once.

Root cause, traced directly in `bot.log`'s live output from the current (13:40 UTC) restart:
`regime_router.py` (new 2026-09-09, replacing the old per-strategy symbol universes with a
live IB-scanner-driven shared pool) does, on every cache-cold start, a **synchronous,
per-symbol IB round trip for every one of up to 50 scanner candidates** — a 90-day daily-bar
fetch for regime classification, then for anything that passes, a second `7200`-bar **minute**
fetch for the chaos-filter check (`_is_chaotic`, `regime_router.py:165`). Watching tonight's
restart in real time, each symbol's minute-bar fetch alone takes ~10 seconds
(`13:40:15.253 → 13:40:25.606` for one symbol, repeating for TNON/GDHG/FTFT/NIO/TPET/RXT/
MSTZ/OPEN/… in the log). At that rate a full 50-candidate refresh is many minutes —
`scripts/watchdog.sh`'s `STARTUP_GRACE_SECONDS=150` (2.5 min) was sized for the bot's
pre-2026-09-09 startup cost, not this. Every restart forces `regime_router.py`'s in-memory
`_cache` back to empty, so the *next* process also starts a full cold refresh, which also
can't finish inside 150s, so it also gets killed — a self-reinforcing loop with no way out on
its own. The one lucky hour this morning is consistent with the watchdog's "within cooldown,
skipping restart" grace occasionally buying just enough extra time for a refresh to complete.

This is not a hypothetical — it has cost the entire trading day so far (last confirmed
successful iteration stretch ended 05:50 ET) and, as of this writing, is still ongoing (the
process running right now was restarted at 13:40 UTC and is mid-refresh).

**Proposed fix #1 (primary) — persist `regime_router.py`'s routed cache to disk so a restart
doesn't force a cold, synchronous re-scan:**

```python
# regime_router.py
import json
import os

_cache = {"routed": {}, "last_refresh": 0.0}
_CACHE_FILE = "regime_router_cache.json"


def _load_cache_from_disk():
    try:
        with open(_CACHE_FILE) as f:
            data = json.load(f)
        if time.time() - data.get("last_refresh", 0) < CACHE_TTL_SECONDS:
            return data
    except (FileNotFoundError, json.JSONDecodeError, KeyError):
        pass
    return None


def _save_cache_to_disk():
    try:
        with open(_CACHE_FILE, "w") as f:
            json.dump(_cache, f)
    except OSError as e:
        logger.warning(f"Regime router: failed to persist cache: {e}")


# at the top of _refresh(), before the cache-age check:
def _refresh(strategy):
    now = time.time()
    if not _cache["routed"]:
        disk_cache = _load_cache_from_disk()
        if disk_cache is not None:
            _cache.update(disk_cache)
    if _cache["routed"] and now - _cache["last_refresh"] < CACHE_TTL_SECONDS:
        return
    ...
    _cache["routed"] = routed
    _save_cache_to_disk()
```

This means a restart mid-TTL-window reuses the last good routing table instantly instead of
re-scanning from zero — breaking the loop directly, and also avoiding real, wasted IB scanner
+ historical-data load every time the watchdog fires.

**Proposed fix #2 (backstop) — widen the cold-start grace period**, since even with disk
persistence, the very first run ever (no cache file yet) or a TTL-expired restart still needs
room to do one real full scan:

```diff
--- a/scripts/watchdog.sh
+++ b/scripts/watchdog.sh
-STARTUP_GRACE_SECONDS=150
+# 2026-09-10: regime_router.py's cold-cache first refresh can take several
+# minutes (up to ~50 scanner candidates x a real IB historical-data round
+# trip each, ~10s/symbol observed live) -- 150s was sized before that
+# existed and was causing a self-reinforcing restart loop (every restart
+# forced a new cold refresh that also couldn't finish in time). Widened
+# to give one real scan room to complete; the disk-persisted cache
+# (regime_router.py) is the real fix for repeat restarts, this is just a
+# backstop for the genuinely-first cold start.
+STARTUP_GRACE_SECONDS=900
```

**Confidence**: High that this is the correct root cause — I watched it happen live in
tonight's restart (symbol-by-symbol ~10s stalls matching exactly `regime_router.py`'s code
path) and the timeline lines up exactly with `watchdog.log`'s restart history and `bot.log`'s
zero-fills telemetry. Medium-high confidence in the specific fix: disk persistence is a
standard, low-risk pattern, but I haven't run it live — worth a human sanity-check on file
permissions/concurrent-write safety (`ib_aux`/pod threads don't touch this file, so a single
writer should be safe, but confirm before deploying). 900s for `STARTUP_GRACE_SECONDS` is a
generous guess, not measured against a real cold run start-to-finish — if a full 50-candidate
scan genuinely takes longer, raise it further or reduce `SCANNER_NUMBER_OF_ROWS`.

**Risk**: Fix #1 means a restart could trade on a routing table that's up to `CACHE_TTL_SECONDS`
(30 min) stale rather than always-fresh — an acceptable tradeoff given the alternative is
"never trades," but worth knowing. Fix #2 alone (without #1) would let the bot go up to 15
minutes with no live monitoring loop responding after a genuine crash (not just this
particular stall pattern) before the watchdog acts — I'd deploy both together rather than #2
alone. Neither change is something I can test end-to-end from here (no bot control in this
session) — flagging clearly rather than guessing further.

## Proposal 1 — Close the WLDSW and TRAD.U positions (or have the human verify and close)

**What**: Sell the live open positions in `WLDSW` (53 shares, opened by `breakout` at
13:39:25 today) and `TRAD.U` (21 shares, opened by `momentum` at 13:39:24 today). I can't
place these orders myself (no order tool in this session) — this needs a human via the
dashboard or `proposals/approve_proposal.py --symbol WLDSW --side sell --quantity 53` /
`--symbol TRAD.U --side sell --quantity 21` (verify the live quantity first — a few cycles
have passed since I captured this).

**Why**:
- Both symbols are the wrong instrument type for every one of these strategies. I checked
  both via web search:
  - `WLDSW` = **Wearable Devices Ltd. warrant** (WLDS is the common stock; WLDSW is the
    warrant on it — a leveraged, time-decaying derivative, not equity). [Nasdaq: WLDSW](https://www.nasdaq.com/market-activity/stocks/wldsw), [Bloomberg: WLDSW](https://www.bloomberg.com/quote/WLDSW:US)
  - `TRAD.U` = **Apex Tech Acquisition Inc. SPAC unit** (common stock + fractional warrant
    bundle, price normally anchored near trust value until a deal is announced — not a
    normal trending/momentum name). [MarketBeat: TRAD.U](https://www.marketbeat.com/stocks/NYSE/TRAD-U/)
  - None of `breakout`/`momentum`/`mean_reversion`/etc.'s entry logic, or the meta-model
    confidence gate, was ever validated against warrants or SPAC units — the strategies'
    own regime/technical reads on these are reading a derivative's or unit's price series
    as if it behaved like common stock.
  - `signals.db` and `bot.log` both currently show `mean_reversion` and `reversal` firing
    SELL on both symbols every cycle since entry — blocked only by the per-symbol
    ownership lock (only breakout/momentum, the opening strategies, can close what they
    opened). Two other strategies' own technical read already disagrees with holding these.
- The WLDSW fill itself looks like a real execution problem, independent of the
  instrument-type issue: `bot.log` line 386523 — order placed as "53.0000x WLDSW @ $4.64"
  (the reference price used for sizing), but line 386577 shows the actual fill at
  **$24.18** — 5.2x the reference price. That's $1,281.54 of actual notional against an
  intended ~$246. TRAD.U slipped too, though far less badly: ordered at $11.52 (line
  386498), filled at $12.45 (+8%). This is the same *shape* of incident as the real
  $100,271 TSLA fill from 2026-09-08 (see `project_100k_tsla_incident_and_hard_ceiling_fix`
  memory) — a market order filling far from the price the sizing decision was based on —
  just triggered by thin-liquidity slippage on a warrant rather than a misreported
  buying-power figure. The existing hard-ceiling/sanity-check code
  (`strategy_manager.py` ~2404-2460) only bounds the *sizing input*
  (portfolio_value/cash); nothing currently checks whether the *fill* came back sane
  relative to what was ordered.

**Confidence**: High that these are the wrong instrument type and shouldn't have been
traded — that's a straightforward category-of-asset mismatch, confirmed via two
independent web sources per symbol. Medium on the exact current unrealized P&L (I don't
have live broker position/mark-price access in this session — the human should check the
dashboard before selling, since price could have moved either direction since the fill).

**Risk**: If left open, WLDSW in particular carries warrant-specific risk on top of the
already-bad entry price — time decay toward its 2027-08-25 expiration, and continued

could also print at a bad price for the same liquidity reason — worth checking the current
quote/spread on the dashboard before selling, not just market-selling blind.

## Proposal 2 — Code fix: `regime_router.py` never applies the existing warrant/unit filter

**What**: `regime_router._discover_candidates()` (the live pipeline that actually produced
today's WLDSW/TRAD.U candidates — confirmed via `regime_router_cache.json`, which has
WLDSW/TRAD.U in the `vwap`/`momentum`/`breakout`/`gap_and_go`/`scalping`/`market_profile`
pools right now) calls `symbol_screener.fetch_alpaca_screener_candidates()` directly and
only filters the result by price band (`SCANNER_MIN_PRICE`/`SCANNER_MAX_PRICE`). It never
calls `symbol_screener.quality_filter_symbols()` — the function that already exists in
this same repo specifically to drop exactly this category (its own docstring: *"warrants/
rights/units (via Alpaca's own asset name)... non-fractionable names"*, checking
`asset.name` for `"warrant"`/`"right"`/`"unit"` via Alpaca's `TradingClient.get_asset()`,
plus dropping non-fractionable assets — which would *also* have caught today's WLDSW/
TRAD.U "not fractionable" order-rejection noise in the log for free). That filter is still
used by the *old* pipeline (`symbol_screener.build_universes()` → `symbol_universes.json`),
but the router that's actually live now bypasses it entirely. This is a real regression,
not a design choice — nothing in `regime_router.py`'s extensive module docstring says this
exclusion was deliberately dropped; the 2026-09-10 Alpaca-reversal rewrite of
`_discover_candidates()` just never re-wired it in.

Proposed diff (`regime_router.py`):

```diff
--- a/regime_router.py
+++ b/regime_router.py
@@
-from symbol_screener import fetch_alpaca_screener_candidates
+from symbol_screener import fetch_alpaca_screener_candidates, quality_filter_symbols
@@ def _discover_candidates(strategy) -> list:
     try:
         raw = fetch_alpaca_screener_candidates()
         if not raw:
             return []
+        raw = quality_filter_symbols(raw)
+        if not raw:
+            return []
         prices = _get_latest_prices_alpaca(raw)
         filtered = [s for s in raw if s in prices and SCANNER_MIN_PRICE <= prices[s] <= SCANNER_MAX_PRICE]
         return filtered[:SCANNER_NUMBER_OF_ROWS]
```

**Why**: Directly closes the gap that let WLDSW/TRAD.U into today's candidate pool in the
first place, reusing code this project already wrote, tested, and trusted for exactly this
purpose (`build_universes()` has called it since Phase 3) rather than inventing a new
filter. `quality_filter_symbols()` does one `TradingClient.get_asset()` call per raw
candidate (up to ~150, before the price filter narrows it) — that's a real added cost on
every `CACHE_TTL_SECONDS` (30 min) refresh, but the old pipeline already pays this same
cost, and 30-minute cadence make it a non-issue.

**Confidence**: High. This isn't a hypothesis — I traced the exact code path from today's
live cache file back to the function that builds it, and confirmed by reading both
functions that one calls a filter the other doesn't.

**Risk**: Low. It's an additive filter reusing existing, already-live code — the main
failure mode is `quality_filter_symbols()`'s own network calls timing out or erroring,
which the function already handles by failing open (returns the input unfiltered rather
than raising) per its own code, so worst case this change is a no-op, not a new crash
surface.
